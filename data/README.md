# 模拟舆情数据集

面向 `docs/智能舆情分析平台-PRD.md` 交付的模拟数据资产，覆盖 PRD 决策 **D-03** 要求的 4 类信源，
并附带决策 **D-02** 要求的情感与风险评测集。

数据**不是随机文本**：三个场景各自内置一条有时间线、有因果、有情绪演变的剧情。
这是「突发预警」「传播溯源」「观点聚类」三条链路能跑出有意义结论的前提——随机数据在这三条链路上什么都演示不出来。

## 快速开始

```bash
# 1. 生成小样本（默认，2 秒内完成，适合开发期反复重建）
python data/generator/generate.py

# 2. 放量到 PRD 规模（内容 1 万 / 评论 8 万，约 3 秒）
python data/generator/generate.py --scale prd

# 3. 复现同一份数据（固定种子与时间锚点）
python data/generator/generate.py --scale small --seed 42 --end-time "2026-10-14 12:00:00"

# 4. 导入 MySQL
mysql -u root -p < data/sql/00_schema.sql
mysql -u root -p < data/sql/90_import_all.sql
```

`90_import_all.sql` 使用 `source` 语句串联各分片，**需与其余 SQL 文件位于同一目录**执行。

### 参数

| 参数 | 说明 | 默认 |
|------|------|------|
| `--scale` | `small`（内容 500 / 评论 6k）或 `prd`（内容 1 万 / 评论 8 万） | `small` |
| `--seed` | 随机种子，同参数下输出完全可复现 | `42` |
| `--end-time` | 剧情结束时间，默认取当前时间（剧情回溯 72 小时） | 当前时间 |
| `--out` | 输出根目录 | `data/` |
| `--dump-samples` | 额外导出带隐藏标签的全量样本（体积较大） | 关闭 |

> `--end-time` 默认取运行时刻，是为了保证导入后「最近 24 小时」的趋势图与预警列表有数据。
> 若需要固定不变的数据集用于对拍，请显式指定该参数。

## 三个场景

| 场景 | 风险等级 | 主导信源 | 剧情要点 |
|------|---------|---------|---------|
| 消费电子质量争议<br>「星耀科技 X-Phone 15」 | S | 社交媒体 + 行业论坛 | 零星用户反馈 → 数码博主深度评测引爆 → 论坛技术长帖 → 媒体跟进 → 官方声明转向 → 水军刷量介入 |
| 连锁餐饮食品安全<br>「味鲜居」 | A | 短视频 | 顾客曝光视频 → 10 分钟内同城跟拍陡增 → 监管部门回应 → 消费者集中诉求 → 品牌致歉整改 → 转缓 |
| 行业政策利好（对照）<br>新能源汽车购置税减免 | C | 新闻门户 + 行业论坛 | 政策公告 → 财经媒体解读 → 论坛产业讨论，以正向与中性为主 |

第三个场景是**对照组**，用途有二：验证情感分布图不全是负面；验证正向舆情不会误报高危预警。

所有品牌、产品、机构、媒体、账号**均为虚构**，不影射任何真实主体。

### 数据中刻意埋入的演示要素

| 要素 | 位置 | 用途 |
|------|------|------|
| KOL 引爆节点（86 万粉 / 134 万粉） | 场景 1、2 | 账号权重评估、高危账号发声告警 |
| 单小时负向声量激增（+500% 以上） | 场景 2 | 触发「1 小时负向声量环比激增」预警规则 |
| 水军刷量（6 个低粉账号，10 分钟内发高度相似文本） | 场景 1、2 | SimHash 去重与刷量识别演示 |
| 官方回应后的情绪转向 | 场景 1、2 | 处置效果与舆情平息曲线 |
| 层级回复（`parent_comment_id` / `reply_to_post_id`） | 全部评论表 | 观点聚类与讨论树 |
| 正向对照场景（无高危触发） | 场景 3 | 预警假阳性测试 |

## 数据模型

共 **9 张表**，库名 `sentiment_monitor`。

### 复用课程的表（字段原样，一字未改）

> 下表的记录数是**参考值**——实际条数随 `--end-time` 与随机数序列浮动。
> 以 `python -m engines.common.db.init_db --status` 的实测结果为准。

| 表 | 信源 | 记录数（small / prd，参考） |
|----|------|---------------------|
| `weibo_note` | 社交媒体-内容 | 241 / 4806 |
| `weibo_note_comment` | 社交媒体-评论 | 2678 / 36517 |
| `douyin_aweme` | 短视频-内容 | 102 / 1997 |
| `douyin_aweme_comment` | 短视频-评论 | 1082 / 14526 |

这四张表刻意保留了两个平台之间的**字段命名差异**，例如 `comment_count`（抖音）vs `comments_count`（微博）、
`like_count`（抖音评论）vs `comment_like_count`（微博评论）、抖音独有的 `sec_uid` / `short_user_id`。

> 这是**有意为之，不要"顺手统一"**。它正是 PRD 中「接入层字段映射」需求的真实来源：
> 后端必须通过映射把平台差异收敛为内部统一字段，上层分析逻辑不得感知平台差异。

### 新增的表

| 表 | 用途 | 记录数（small / prd） |
|----|------|---------------------|
| `platform_account` | 账号主数据：粉丝量、认证类型、影响力评分、疑似水军标记 | 385 / 4825 |
| `news_article` / `news_article_comment` | 新闻门户内容与评论 | 92 / 1822，1376 / 17413 |
| `forum_thread` / `forum_post` | 行业论坛主帖与回帖（含楼层号与引用关系） | 70 / 1376，957 / 12608 |

新增表沿用课程的命名与类型习惯（业务 ID 与主键分离、时间戳与日期字符串双写、互动量用 `text` 存储），
使接入层只需维护一套映射规则。

### 为什么要单独建 `platform_account`

课程的两张内容表**都没有粉丝量字段**，而 PRD 的 FR-29「账号权重评估」必须有它。
把账号信息补在独立表里，既能满足需求，又不必改动课程表结构。
`influence_score` 由粉丝量取对数并叠加认证类型权重推导（0~100），可直接作为热度计算的账号因子。

### 关联关系

评论通过**业务 ID** 关联内容，不是主键：

| 评论表 | 关联字段 | 指向 |
|--------|---------|------|
| `weibo_note_comment` | `note_id` | `weibo_note.note_id` |
| `douyin_aweme_comment` | `aweme_id` | `douyin_aweme.aweme_id` |
| `news_article_comment` | `article_id` | `news_article.id` |
| `forum_post` | `thread_id` | `forum_thread.thread_id` |

## 自检

每次生成后自动执行 7 项检查，无需数据库：

| 检查项 | 内容 |
|--------|------|
| 信源覆盖 | 4 类信源均有内容与评论 |
| 外键完整性 | 每条评论都能追溯到存在的内容宿主 |
| 时间分布 | 全部记录落在 `[结束时间-72h, 结束时间]` 内 |
| 情感分布 | 各场景实际分布与剧本预期偏差 ≤ 12% |
| 预警可触发 | 存在单小时负向声量环比增幅 > 50% 的时段（且前序基数 ≥ 3，过滤噪声波动） |
| SQL 结构 | 列名与 schema 一致、值个数匹配、字符串引号闭合 |
| 输出完整性 | 7 个 SQL 文件齐全、行数与内存一致、评测集达标 |

SQL 结构校验是**在没有数据库凭据时能做的最严格检查**——转义错误、列错位、引号未闭合
恰恰是导入失败最常见的原因，这些都会在这里暴露。

> ⚠️ 生成的 SQL **尚未在真实 MySQL 实例上做过导入实测**（开发环境缺少数据库凭据）。
> 首次导入前请先确认 `mysql` 连接可用；若报错，请把错误信息反馈以便修正 `emitter.py` 的转义逻辑。

## 关于 `sql/legacy/`

课程提供的真实爬取数据（微博 + 抖音，内容 142 条 / 评论 2023 条，主题为高考与 NBA 总决赛）。

**不要把它和三个企业场景混入同一监测主题**——主题不同，混入会污染词包与语义聚类。
它的价值是作为「公共事件」主题的真实样例，以及验证接入层对真实爬取数据的兼容性
（我们生成的表结构就是对齐这批数据设计的）。

注意其原始文件写入的是 `media_crawler_v1` 库，导入前需调整库名。

## 已知限制

1. **评测集随数据规模变化**。风险评测集的等级分布依赖候选窗口数量，small 档 S 级样本仅 5 条，
   prd 档可达 24 条。**正式评测请使用 `--scale prd` 生成的数据**，否则高等级样本过少，
   评测结果不具代表性。
2. **文案库有限**。模板变体数量在 prd 规模下会出现明显重复（除水军批次外）。
   若需要更自然的大规模语料，应扩充 `scenarios.py` 的文案库或引入真实语料。
3. **互动量是合成的**。由角色基准 × 账号影响力 × 对数正态抖动生成，量级关系合理但非真实分布。
4. **时间锚点默认取运行时刻**。不指定 `--end-time` 时，两次生成的数据时间不同，无法逐行对拍。
